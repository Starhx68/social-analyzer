# 部平台接口对接方案 (Draft)

## 1. 方案概述

本方案落实《以旧换新2026部平台通用接口-接入技术规范v20251227(1).pdf》中关于订单数据上报的要求。
主要涉及两个核心对接场景：
1.  **4.4 节**: 补贴资格数据核销 (2026版) - 对应全品类资料完善后的核销上报。
2.  **4.5 节**: 手机等数码产品购新和家电以旧换新交易数据 - 对应3C/家电类订单的实时交易上报。

## 2. 接口定义

### 2.1 (4.4节) 补贴资格数据核销接口

*   **接口名称**: 补贴资格数据核销(2026版)
*   **接口地址 (生产)**: `https://open-yjhx.chinaums.com/v1/market/subsidy/qualification/confirm-2026`
*   **请求方式**: POST (JSON)
*   **认证方式**: Header `Authorization`

**数据结构**:
顶层字段包含 `province`, `reqSsn` 等，核心业务数据在 `data` 数组中。

### 2.2 (4.5节) 交易数据实时上报接口

*   **接口名称**: 手机等数码产品购新和家电以旧换新交易数据
*   **接口地址 (生产)**: `https://open-yjhx.chinaums.com/v1/market/subsidy/qualification/upload-trans-2026`
*   **请求方式**: POST (JSON)
*   **认证方式**: Header `Authorization`

**数据结构**:
单条上送，无 `data` 数组包裹。

## 4. 缺失字段与风险评估

### 4.1 严重缺失字段 (Blocker)
以下字段在现有 `orders` / `order_sync` 表中未明确定义，且接口设为**必填**：

1.  **`uniscid` (销售企业统一社会信用代码)**:
    *   目前只有 `mchnt_no` (商户号)。需确认 `mchnt_no` 是否即为信用代码，或者需要在 `organizations` 表中增加 `credit_code` 字段。
2.  **`barcode` (商品条码)**:
    *   目前有 `product_model`，但未见 `barcode` (69码)。需检查 Oracle 同步数据 `extra_info` 中是否有 `GOODS_BARCD` 或类似字段。
3.  **`acquirer` (收单机构) & `paymentId` (支付编号)**:
    *   支付相关信息目前未同步。需确认是否从 Oracle 同步，或是否有默认值（如 "银联商务" / "0000"）。
4.  **`buyer_name` & `buyer_phone`**:
    *   `orders` 表有 `buyer_id_code`，但姓名和手机号目前可能仅在 `extra_info` 或未同步。需确认隐私合规及数据来源。

### 4.2 业务逻辑确认事项
1.  **`cateCode` 映射**: 我们的 `product_category_code` (如 "A01") 是否与部平台标准一致？
2.  **`isAIProduct` & `pcType`**: 如何判断？是否需要增加商品属性配置表？
3.  **`oldThings` (交旧)**: 系统中是否有字段标识该订单是否涉及交旧？

## 5. 建议技术方案

1.  **数据库扩展**:
    *   `organizations`: 增加 `credit_code` (统一社会信用代码), `acquirer_name` (默认收单机构)。
    *   `orders` / `order_sync`: 增加 `buyer_name`, `buyer_phone`, `product_barcode`, `payment_id`, `acquirer`, `is_ai_product`, `pc_type`, `is_trade_in`。
2.  **数据同步升级**:
    *   修改 `OrderSyncService`，从 Oracle 原始数据中提取上述缺失字段（如 `NOTICE_DATA` 中可能包含支付信息）。
3.  **默认值策略**:
    *   对于无法获取的非关键字段（如 `acquirer`），可配置系统级默认值作为临时方案。
